# ML Testing: Validating Prediction Logic Against Famous People

> **Status**: Both phases below are implemented in `MatchMLPipeline/DashaValidationPipeline.cs`
> (Phase 1) and `MatchMLPipeline/KutaValidationPipeline.cs` (Phase 2), and have been run
> end-to-end against a locally-seeded copy of the real HuggingFace datasets
> (`MatchMLPipeline/CsvSeeder.cs`; see "Seeding and running" below). Run either via
> `MatchMLPipeline/Program.cs`'s `Main2` (uncomment the relevant `RunAndPrintReport()` line) -
> requires a local Postgres with the HuggingFace datasets already loaded into it. The sketches
> below are kept as-is since the shipped code follows them closely; where the real
> implementation differs (e.g. the actual field name behind "Rodden AA" linkage, or swapping the
> brute-force Dasha scan for an analytic one - see "Real run results" below), that's noted
> inline.

## Goal

We have real astrology-prediction logic (Vimshottari Dasha timing, Kuta/Guna compatibility
scoring) and a real dataset of ~15,000 famous people with astrologer-verified ("Rodden AA")
birth data. This document sketches a concrete pipeline that closes the loop: run our own
prediction logic against these real birth charts, and check whether it lines up with
real, documented life events (marriage dates, to start) for the same people.

This is a **validation harness**, not a new feature — it produces an accuracy number and a
list of misses, nothing else. It follows the same pattern `MatchMLPipeline/DatasetFactory.cs`
already established (standalone console project, `IDbContextFactory<AppDbContext>` wired by
hand, reusing the API's repositories) rather than introducing a new architecture.

## Existing building blocks (already in the repo)

| Piece | Location | Role |
|---|---|---|
| Birth data for ~15k real people, Rodden AA rated | `HuggingFace/PersonList-15k.csv` (via `IPersonRepository`) | Ground-truth chart inputs |
| Marriage dates/outcomes for a subset of those people | `HuggingFace/MarriageInfoDataset.csv` (via `IMarriageInfoDatasetRepository`) | Ground-truth outcomes to check against |
| Dasha timing logic | `Library/Logic/Calculate/VimshottariDasa.cs` (`CurrentDasa8Levels`, `DasaCountedFromInputDasa`, `TimeLeftInBirthDasa`, …) | Produces predicted time windows |

| Pipeline scaffolding pattern | `MatchMLPipeline/DatasetFactory.cs` | Reuse its DB-wiring and repository-access pattern for the new validation project |

## What "well-known predictions" means concretely here

`MarriageInfoDataset.csv` is the only outcome dataset with enough volume to be useful today
(body-type/appearance predictions exist as a stub but aren't populated). So the first, concrete
validation target is:

> **For a person whose actual marriage date is known, does Vimshottari Dasha analysis of their
> birth chart flag a "marriage-favorable" period that contains that date?**

This sidesteps the fact that Kuta/Guna matching is inherently a *two-chart* comparison (it scores
compatibility between two people, it doesn't by itself predict *when* a single person marries).
Marriage-timing prediction in this codebase is a Dasha-period question, not a Kuta question — so
Kuta validation is a separate, second-phase exercise (see "Phase 2" below), not part of the
initial pipeline.

## Phase 1 pipeline: Dasha-predicted marriage window vs. actual marriage date

### 1. Build the candidate set

Not all 15k rows are usable — most `MarriageInfoDataset.csv` entries were generated by an LLM
(`GetRawMarriagesFromPersonProfileLLM_LLAMA3` in `DatasetFactory.cs`) and carry a self-reported
`dataCredibility` field, and many `marriageDate` values are year-only, `"None"`, or `"N/A"`.
Filter down to a clean candidate set first:

```csharp
// New file: MatchMLPipeline/DashaValidationPipeline.cs (same project, same repo-wiring pattern
// as DatasetFactory.cs — reuses personRepo / marriageInfoDatasetRepo, no new DB access code)

public record MarriageCandidate(PersonListEntity Person, DateTime MarriageDate, string Credibility);

public static List<MarriageCandidate> BuildCandidateSet()
{
    var people = personRepo.GetAllAsync().GetAwaiter().GetResult()
        .Where(p => p.Notes.Contains("\"rodden\": \"AA\"")); // only astrologer-verified birth data

    var marriages = marriageInfoDatasetRepo.GetAllAsync().GetAwaiter().GetResult();

    var candidates = new List<MarriageCandidate>();
    foreach (var person in people)
    {
        var record = marriages.FirstOrDefault(m => m.PartitionKey == person.RowKey);
        if (record == null) continue;

        foreach (var marriage in ParseMarriagesJson(record.Info))
        {
            if (marriage.DataCredibility != "high") continue;          // drop low/medium confidence
            if (!TryParseFullDate(marriage.MarriageDate, out var date)) continue; // drop year-only/"None"/"N/A"

            candidates.Add(new MarriageCandidate(person, date, marriage.DataCredibility));
        }
    }
    return candidates; // expect low hundreds, not 15k, after filtering
}
```

### 2. For each candidate, compute the Dasha-predicted marriage window

> **Real-run correction**: `VimshottariDasa.DasaPeriodsOld` below (a brute-force life-span scan
> via `EventManager.CalculateEvents` at fine time resolution across all 4 Dasa levels) turned
> out to take 30+ minutes for a *single* candidate in practice - infeasible for ~10k candidates.
> The shipped `DashaValidationPipeline.PredictedMarriageWindow` instead samples
> `VimshottariDasa.CurrentDasa8Levels` (the same O(1) analytic point-in-time lookup the live
> API/Muhurtha logic already uses) once a month across the scan range - a few thousand times
> cheaper per candidate, at the cost of ~1-month resolution on window boundaries instead of an
> exact antardasha start/end (acceptable given windows are already compared to real dates at
> the day level with mean window width tracked separately anyway).

```csharp
public static (DateTime windowStart, DateTime windowEnd) PredictedMarriageWindow(Time birthTime)
{
    // Reuse existing Dasha machinery — no new astrology logic, just a query over it.
    var dasaEvents = VimshottariDasa.DasaPeriodsOld(birthTime, levels: 2, scanYears: 100);

    // "Marriage favorable" period = sub-periods (antardasha) ruled by planets classically
    // associated with marriage/relationship (Venus, 7th-lord, Jupiter for women per BPHS) —
    // this classification rule itself needs sign-off from whoever owns the astrology logic;
    // it is the one genuinely new piece of domain logic this pipeline introduces.
    var candidateWindows = dasaEvents.Where(e => IsMarriageFavorablePeriod(e));

    // naive first pass: just take the first favorable window after age 18
    var first = candidateWindows.FirstOrDefault(w => w.StartTime > birthTime.AddYears(18));
    return (first.StartTime, first.EndTime);
}
```

### 3. Compare predicted window to actual date

```csharp
public record ValidationResult(string PersonName, DateTime Actual, DateTime WindowStart, DateTime WindowEnd, bool Hit);

public static List<ValidationResult> RunValidation(List<MarriageCandidate> candidates)
{
    var results = new List<ValidationResult>();
    foreach (var c in candidates)
    {
        var birthTime = ParseBirthTime(c.Person.BirthTime); // existing Time-parsing helper, not new
        var (start, end) = PredictedMarriageWindow(birthTime);

        var hit = c.MarriageDate >= start && c.MarriageDate <= end;
        results.Add(new ValidationResult(c.Person.Name, c.MarriageDate, start, end, hit));
    }
    return results;
}
```

### 4. Report

```
Accuracy = hits / total candidates
Mean window width (years) = average(end - start) across all candidates
```

A window-hit rate alone is easy to game (a 20-year window "predicts" almost everything) — so
**always report accuracy alongside mean window width**, and treat a run that improves accuracy
by widening the window as a regression, not a win. A simple table dump (person, actual date,
predicted window, hit/miss) sorted by miss-first is enough to eyeball where the logic breaks
down; no dashboard needed for a first pass.

## Phase 2: Kuta/Guna compatibility validation (implemented)

A second, independent pipeline validates `MatchReportFactory`'s Kuta scoring using the
*married couples where both people are linkable to a Rodden AA row in `PersonList-15k.csv`*.
This is a much smaller candidate set than Phase 1: of the ~17,900 marriage entries in
`MarriageInfoDataset.csv`, only ~1,450 have their spouse linked back to a `PersonList-15k` row
via a populated `PersonId` field (the rest only capture the spouse's *name* as free text) — that
linkage is what the existing `GetMarriagesWhereRoddenAA()` extension method filters for (its
name refers to the linkage step, not a Rodden rating on the spouse). Of outcome labels present,
only `"Happiness"` (~11.6k) and `"Dissolution"` (~4.9k) are used as a clean binary signal;
`"Struggle"`/`"Tragedy"`/`"Unknown"`/etc. are dropped as ambiguous.

Rather than calling `GunaKuta`/`NadiKuta`/etc. individually, `KutaValidationPipeline.cs` reuses
`MatchReportFactory.GetNewMatchReport(male, female, userId)` directly — it already runs every
Kuta calculator and sums them into `report.KutaScore`, which is the same total score the live
match-report feature shows users, so validating it validates what's actually shipped. For each
linked couple it computes a Spearman rank correlation between `KutaScore` and outcome
(Happiness=1/Dissolution=0), plus mean score per outcome group — a ranking/correlation check,
not a hit/miss window like Phase 1, since Kuta scoring claims relative compatibility, not a
specific date.

## Real run results (2026-09-12, local dev Postgres)

Seeded via `CsvSeeder.SeedAll` (15,807 people, 15,807 marriage-info records, one per person)
and run end-to-end via `Program.cs`'s `Main` temporarily:

**Phase 1 (Dasha marriage-window)**: 10,750 candidates after filtering (Rodden AA + high
credibility + fully-dated marriage) — much larger than this doc's original "low hundreds"
estimate, since most of the dataset turned out to be high-credibility and fully dated.

```
Accuracy (actual date inside predicted window): 9.4% (1015/10750)
Mean window width: 1.9 years
```

9.4% against a ~2-year window inside a ~50+ year adult lifespan (age 18 to scan end) is close
to what a *random* 2-year window would hit by chance alone (roughly 2/52 ≈ 4-8% depending on
how much of the range is favorable) — this Dasha-timing heuristic is not clearly beating chance
on this sample. That's a real, useful finding: either `IsMarriageFavorableLord`'s classification
rule (Venus/7th-lord/Jupiter-for-women) is too coarse, or first-marriage timing needs a
different signal than "the first favorable antardasha after 18," or both. Not a reason to
distrust the pipeline — it's the pipeline doing its job.

**Phase 2 (Kuta/Guna compatibility)**: 1,258 linked couples with a clean outcome label; 1,105
successfully scored (some skipped — same-gender pair in source data, or a Kuta calculator
threw).

```
Mean Kuta score - Happiness outcomes (599): 45.07
Mean Kuta score - Dissolution outcomes (506): 47.41
Spearman correlation (Kuta score vs. Happiness=1/Dissolution=0): -0.062
```

Dissolution-outcome couples scored marginally *higher* on average than Happiness-outcome
couples, and the rank correlation is essentially zero (slightly negative). On this sample, total
Kuta score does not track real marriage outcomes. Worth double-checking before drawing strong
conclusions: whether 36 (the traditional "minimum recommended" total) is being crossed by most
of both groups regardless of outcome, and whether individual Kuta factors (not just the summed
total) carry more signal than the sum does.

## Bugs found and fixed along the way

Building and running this pipeline against real data surfaced several real, pre-existing (or
newly-introduced) bugs. Listed in the order they were hit:

1. **Rodden-AA filter matched zero people** (`DashaValidationPipeline.cs`,
   `KutaValidationPipeline.cs`). Both `BuildCandidateSet()`/`BuildCoupleCandidateSet()` originally
   filtered `PersonListEntity.Notes` with `Contains("\"rodden\": \"AA\"")` — valid *JSON*
   double-quote syntax. The actual data in `PersonList-15k.csv`'s `Notes` column is
   Python-dict-style single quotes: `{'rodden': 'AA'}`. The filter would have silently returned
   an empty candidate set every run. **Why it happened**: assumed JSON without checking a real
   row first. **Fix**: match the single-quoted form instead, with a comment noting the format.

2. **`VimshottariDasa.DasaPeriodsOld` took 30+ minutes for a single candidate** (see "Real-run
   correction" under Phase 1 above) — a brute-force scan via `EventManager.CalculateEvents`
   across ~351 tagged astrological rules × ~1,739 time samples (100 years at 504-hour
   resolution), all 4 Dasha levels every time. **Why it happened**: this method is generic
   Muhurtha/event-finder infrastructure repurposed for Dasha timing, not built for it — real
   Vimshottari Dasha is a closed-form sequence, not something that needs scanning. **Fix**:
   `PredictedMarriageWindow` now samples `VimshottariDasa.CurrentDasa8Levels` (an O(1) analytic
   lookup, same one the live API/Muhurtha logic already uses) monthly instead, cutting per-candidate
   time from ~30 minutes to ~0.03-0.05 seconds.

3. **`VimshottariDasa.DasaPeriodsOld`'s `levels` parameter was dead code** (`Library/Logic/Calculate/VimshottariDasa.cs`).
   Discovered while diagnosing #2: the method accepts a `levels` argument but its body always
   built `tagList` with all 4 hardcoded PD tags regardless of what was passed in — so a caller
   asking for `levels: 2` silently paid for all 4 levels anyway. **Why it happened**: the tag
   list was written before the `levels` parameter was added (or the parameter was added without
   wiring it through) and nothing ever exercised it enough to notice. **Fix**: `tagList` is now
   `allLevelTags.Take(Math.Clamp(levels, 1, allLevelTags.Count))`, so the parameter is honored.
   This method has zero live callers anywhere in the codebase (API/Website/WebsiteNative/tests),
   so the fix has no behavioral impact on the running product — it only fixes the bug for
   whichever future caller (like this pipeline almost was) relies on `levels` actually working.

4. **Wrong local DB password, causing a silent fallback** (`MatchMLPipeline` project). Neither
   pipeline nor `CsvSeeder` had a `dotnet user-secrets` connection string configured, so
   `DatasetFactory.CreateDbContextFactory()` fell back to its hardcoded placeholder password
   (`postgres`) instead of the real local dev password in `API/appsettings.Development.json`,
   causing an `Npgsql.PostgresException: password authentication failed`. **Fix**: set the real
   connection string via `dotnet user-secrets set "ConnectionStrings:Postgres" "..."` scoped to
   the `MatchMLPipeline` project (see "Seeding and running" below).

5. **Nested-parallelism thread-pool starvation** (both pipelines, since fixed by #2 making it
   moot for Phase 1, but the lesson stands for Phase 2 too). An early version wrapped each
   pipeline's per-candidate loop in an outer `Parallel.ForEach`, not realizing
   `EventManager.CalculateEvents` (called transitively via the old `DasaPeriodsOld` path) already
   ran its own internal `Parallel.ForEach`/`Parallel.For`. Stacking an outer parallel loop on top
   oversubscribed the thread pool rather than speeding anything up. **Fix**: both
   `RunValidation()` methods run sequentially with periodic throughput logging instead; per-item
   cost is now cheap enough (Phase 1 fixed by #2; Phase 2 was already cheap) that sequential
   execution finishes quickly on its own.

6. **`GetMarriages()` NullReferenceException risk** (`Library/Logic/MatchMLDatasetEntityExtensions.cs`,
   pre-existing shared helper, newly exercised by both pipelines). Threw if a marriage record's
   `Info` JSON parsed successfully but had no top-level `"marriages"` array (e.g. a malformed or
   truncated LLM reply) — and neither pipeline's row-scanning loop guarded against it, so one bad
   row would crash the entire multi-minute run. **Fix**: null-check the `"marriages"` token
   before iterating, returning an empty list instead of throwing.

7. **Silent exception swallowing in `KutaValidationPipeline.RunValidation()`**. A
   `catch (Exception) { continue; }` around `GetNewMatchReport` discarded failures with zero
   logging, unlike this same project's own convention (`DatasetFactory` logs `"FAIL...Moving on"`
   before continuing) — making a lower-than-expected `Scored couples` count unexplainable after
   the fact. **Fix**: log the failing couple's names and the exception message before skipping.

8. **O(n²) batching in `CsvSeeder.InsertInBatches`**. Used `entities.Skip(i).Take(BatchSize)` on
   a `List<T>`, which re-walks the list from the start every batch. Harmless at ~15.8k rows but
   wasteful if the CSVs grow. **Fix**: `entities.GetRange(i, count)` instead — O(1) per batch.

## Seeding and running

```bash
# One-time: point MatchMLPipeline at your local Postgres (same DB the API/Website use)
cd MatchMLPipeline
dotnet user-secrets set "ConnectionStrings:Postgres" "Host=localhost;Port=5432;Database=vedAstro;Username=postgres;Password=<yours>"

# Uncomment the relevant lines in Program.cs's Main2, then:
dotnet run --project MatchMLPipeline/MatchMLPipeline.csproj
```

`CsvSeeder` is idempotent (skips rows already present by primary key) so it's safe to re-run
after a partial load or once the CSVs are updated.

## Caveats to flag before trusting results

- **Ground truth quality**: `dataCredibility` on marriage records is itself LLM-self-reported
  (see `GetRawMarriagesFromPersonProfileLLM_LLAMA3`), not independently verified — treat "high"
  as "the LLM was confident," not as fact-checked.
- **Birth time precision**: Rodden "AA" only rates the *source's* claimed accuracy for
  birth-record collection, not that the resulting Dasha calculation is correct — it rules out
  "no time given" data, nothing else.
- **Sample size after filtering**: expect Phase 1's clean candidate set to be a few hundred
  people at most once low/medium credibility and year-only dates are dropped — enough for a
  directional accuracy signal, not a statistically rigorous benchmark.
- **`IsMarriageFavorablePeriod` is new logic**: it's the one part of this sketch that isn't
  already implemented and tested elsewhere in the codebase, so its own correctness needs
  review before trusting any accuracy number that depends on it.

## Where this lives

Both phases live inside `MatchMLPipeline` (it already has the DB-wiring and repository access
this needs) as `MatchMLPipeline/DashaValidationPipeline.cs` (Phase 1) and
`MatchMLPipeline/KutaValidationPipeline.cs` (Phase 2), each invoked via a commented-out
`RunAndPrintReport()` call in `Program.cs`'s `Main2` — the same opt-in pattern every other
`DatasetFactory` pipeline step already uses. Not part of `API/API.IntegrationTests` since this
is a data-science accuracy check against real biographical data, not a pass/fail correctness
test of an HTTP endpoint.
